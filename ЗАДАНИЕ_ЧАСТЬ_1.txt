  ЗАДАНИЕ: from django.utils import timezone
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py

Зачем timezone.now() вместо datetime.now()?
В Django включён режим «часовых поясов» (USE_TZ = True).
Все даты хранятся в базе в UTC, а отображаются в настроенном поясе (Europe/Moscow).
datetime.now() возвращает «наивное» время без часового пояса — Django
выдаст предупреждение и возможны ошибки сравнения дат.
timezone.now() всегда «осведомлено» о часовом поясе — безопасно.

ГДЕ СОХРАНЯЕТСЯ ДАТА: в базе данных в поле DateTimeField в формате UTC.
Django автоматически конвертирует при чтении в Europe/Moscow для отображения.

  Пример 1 — User.created_at (дата регистрации)
━━━━━━━
Когда пользователь регистрируется, фиксируется точное время.
Это нужно для:
  — приветственных писем через неделю после регистрации
  — фильтрации новых пользователей за последние 30 дней
  — аналитики: сколько пользователей зарегистрировалось в этом месяце

━━━━━━━
  Пример 2 — Prosthesis.created_at (дата добавления в каталог)
━━━━━━━
Когда товар появился в каталоге, фиксируется дата добавления.
Это нужно для:
  — раздела «Новинки» — протезы за последние 30 дней
  — расчёта скидок: чем дольше товар на складе, тем выше скидка
  — сортировки «сначала новые» в каталоге

━━━━━━━
  Пример 3 — Request.created_at (дата создания заявки)
━━━━━━━
Когда клиент оставил заявку, фиксируется момент обращения.
Это нужно для:
  — SLA-контроля: заявки без ответа более 3 дней нужно эскалировать
  — автоматического закрытия заявок через 30 дней без активности
  — статистики по нагрузке: сколько заявок поступает в день/неделю/месяц

Показать: http://127.0.0.1:8000/catalog/requests/ — галочка «За последние 30 дней»
— это фильтр по created_at, работающий через timezone.now().

  ЗАДАНИЕ: class Meta: ordering
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py — каждая модель

Смысл: определяет порядок «по умолчанию» — как записи сортируются при
обращении к ним без явного order_by(). Один раз задаётся в модели —
работает везде (в шаблонах, в views, в admin).

Логика в проекте:
  ordering = ['name']         — справочники сортируются по алфавиту (Role, Tag, ProsthesisType)
  ordering = ['-created_at']  — заявки показываются от новых к старым
  ordering = ['-event_date']  — мероприятия: ближайшие предстоящие вверху
  ordering = ['last_name', 'first_name'] — пользователи как в телефонной книге

Минус перед полем означает «по убыванию»: -created_at — сначала самые новые.

Показать: http://127.0.0.1:8000/catalog/prostheses/ — протезы по алфавиту.
Показать: http://127.0.0.1:8000/catalog/requests/ — новые заявки наверху.

Смысл: ограниченный список допустимых значений для поля.

  ЗАДАНИЕ: related_name — пример использования
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py + catalog/views.py (строка 115)

Смысл: related_name — это имя обратной связи. При создании ForeignKey
Django автоматически создаёт обратную ссылку. Без related_name она называется
«request_set» по умолчанию — не очень читаемо.

Как это работает в проекте:
  В модели Request задано: prosthesis = ForeignKey(Prosthesis, related_name='requests')
  Теперь у объекта «протез» появляется атрибут requests —
  через него можно получить все заявки на этот протез:
    prosthesis.requests.all()   — все заявки
    prosthesis.requests.count() — сколько заявок

Другие related_name в проекте:
  user.requests.all()       — все заявки пользователя
  user.blog_posts.all()     — все статьи, написанные пользователем
  prosthesis_type.prostheses.all() — все протезы этого типа
  role.users.all()          — все пользователи с этой ролью

Показать: открыть страницу любого протеза /catalog/prostheses/1/
Внизу страницы — раздел «Заявки на этот протез». Данные получены именно через
prosthesis.requests.all() — через обратную связь по related_name.

  ЗАДАНИЕ: filter(), exclude(), order_by()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функции prosthesis_list() и orm_demo()

filter() — отбирает записи, которые СООТВЕТСТВУЮТ условию.
  Применяется в prosthesis_list: фильтр по типу, поиск по названию.
  Применяется в request_list: заявки за последние 30 дней, по типу.

exclude() — отбирает записи, которые НЕ соответствуют условию.
  Это противоположность filter().
  В prostehs_list: «скрыть без цены» исключает протезы с пустой ценой.
  В orm_demo: подсчёт активных через exclude(is_active=False) —
  это логически то же самое, что filter(is_active=True), но другим путём.

order_by() — сортирует результат по указанному полю.
  Минус перед полем — по убыванию: '-price' (дорогие первые).
  Несколько полей: order_by('-price', 'name') — сначала по цене, при равной — по имени.

Цепочки: filter, exclude, order_by можно строить цепочкой.
  Каждый вызов возвращает новый QuerySet — SQL запрос ещё не выполняется.
  Запрос к базе происходит только при фактическом использовании данных.

Показать: http://127.0.0.1:8000/catalog/prostheses/
  — галочка «Скрыть без цены» → exclude()
  — выпадающий список «Сортировка» → order_by()
  — текстовый поиск → filter()
Показать: http://127.0.0.1:8000/catalog/orm-demo/
  — две таблицы: через exclude() и order_by()

  ЗАДАНИЕ: __ (двойное подчёркивание) — два варианта
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py

Вариант 1 — оператор (lookup):
  Синтаксис: поле__оператор
  Это способ задать условие сравнения при фильтрации.
  Примеры из проекта:
    created_at__gte   — дата ≥ (greater than or equal)
    price__isnull     — цена IS NULL
    price__gte=100000 — цена ≥ 100 000 руб.
  Показать: галочка «За последние 30 дней» в /catalog/requests/ использует created_at__gte.

Вариант 2 — обращение к связанной таблице:
  Синтаксис: связанная_модель__поле_связанной_модели
  Это способ фильтровать по полям других таблиц без ручного JOIN.
  Примеры из проекта:
    prosthesis_type__name__icontains — искать по названию ТИПА протеза
    user__last_name__icontains       — искать по фамилии ПОЛЬЗОВАТЕЛЯ в заявке
  Django автоматически строит нужный JOIN в SQL.
  Показать: поиск в /catalog/prostheses/ — ищет и по названию протеза,
  и по названию его типа, хотя тип — в другой таблице.

  ЗАДАНИЕ: Собственный модельный менеджер
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py — класс ActiveManager (строки 11–15) и Prosthesis

Смысл: менеджер — это интерфейс для выполнения запросов к БД.
Стандартный менеджер objects возвращает все записи.
Собственный менеджер позволяет задать «предварительный» фильтр,
который будет применяться ко всем запросам через этот менеджер.

В проекте:
  Prosthesis.objects — стандартный (возвращает ВСЕ протезы, включая неактивные)
  Prosthesis.active  — кастомный (только активные, is_active=True)

Зачем это удобно: вместо того чтобы писать filter(is_active=True) в каждом view,
достаточно написать Prosthesis.active.all() — и фильтр уже встроен.
Нельзя «забыть» добавить этот фильтр.

Показать: /catalog/prostheses/ — показываются только активные протезы.
Деактивировать протез в /admin/catalog/prosthesis/ → он исчезнет из списка на сайте.
Показать: /catalog/orm-demo/ — кнопка «Деактивировать» → деактивированные
не попадут в каталог благодаря кастомному менеджеру.

  ЗАДАНИЕ: get_absolute_url + reverse
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py — метод get_absolute_url в каждой модели

Смысл get_absolute_url: каждая модель «знает» свой URL.
Это соглашение Django — если модель имеет эту функцию, другие части
системы могут получить ссылку на объект, не зная URL-схемы.

Смысл reverse: не пишем URL вручную, а получаем его по имени маршрута.
Если URL когда-то изменится — нужно поменять только в urls.py,
все reverse() обновятся автоматически.

Где используется в проекте:
  — В views.py после создания протеза: redirect(prosthesis.get_absolute_url())
    Браузер переходит на страницу созданного объекта.
  — В шаблоне prosthesis_list.html: ссылка на название ведёт на деталь.
  — В admin.py: Django автоматически добавляет кнопку «Просмотреть на сайте»
    для моделей с get_absolute_url.

Показать: создать протез через /admin/ или /catalog/prostheses/create/ →
после сохранения браузер автоматически перешёл на страницу этого протеза.

  ЗАДАНИЕ: Агрегирование и аннотирование — три примера
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция stats()
Показать: http://127.0.0.1:8000/catalog/stats/

Разница между aggregate и annotate:
  aggregate — получить ОДНО итоговое число по всей таблице (напр. средняя цена).
  annotate  — добавить ВЫЧИСЛЯЕМОЕ ПОЛЕ к каждой записи в QuerySet.

aggregate() — итоговые показатели по всем протезам:
  Одним запросом получаем: среднюю, максимальную, минимальную цену, сумму, количество.
  Результат — словарь с вычисленными значениями.
  Показать: раздел «Ценовые показатели» на странице статистики.

annotate() — Пример 1: количество протезов по каждому типу.
  К каждому типу «приписываем» поле prosthesis_count — сколько у него протезов.
  Потом сортируем по этому полю — самые популярные типы наверху.
  Показать: таблица «Протезов по типу».

annotate() — Пример 2: количество заявок по каждому протезу.
  К каждому протезу «приписываем» поле request_count — сколько на него заявок.
  Топ-10 протезов с наибольшим числом заявок — рейтинг популярности.
  Показать: таблица «Заявки на протез (топ 10)».

annotate() — Пример 3: количество статей у каждого пользователя.
  К каждому пользователю — поле post_count.
  После annotate() можно фильтровать по вычисленному полю:
  filter(post_count__gt=0) — только те, у кого есть хотя бы одна статья.
  Показать: таблица «Активность пользователей».

  ВОПРОС: Создание и применение миграций
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Что такое миграция:
Файл Python, описывающий изменение структуры базы данных.
Хранится в папке catalog/migrations/ и является историей изменений схемы БД.
Позволяет воспроизвести точно такую же структуру на любом сервере.

Рабочий процесс:
  1. Изменяем модель (добавляем поле, меняем тип, удаляем таблицу).
  2. python manage.py makemigrations
     Django сравнивает текущие модели с последней сохранённой миграцией
     и создаёт новый файл с описанием изменений.
  3. python manage.py migrate
     Применяет все ещё не применённые миграции к базе данных.
     Физически создаёт/изменяет/удаляет таблицы в SQLite.

Дополнительные команды:
  python manage.py showmigrations   — показывает [X] применённые и [ ] не применённые
  python manage.py migrate catalog 0001  — откатить до конкретной миграции

Почему важно коммитить файлы миграций в git:
  Другой разработчик (или production-сервер) запустит migrate
  и получит точно такую же базу данных — без ручного написания SQL.

  ВОПРОС: Работа с QuerySet и менеджерами
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QuerySet — это «ленивый» запрос к базе данных.
Ленивый означает: запрос строится постепенно, но к базе не обращается,
пока данные реально не понадобятся.

Почему это хорошо:
  — Можно навешивать filter(), exclude(), order_by() один за другим.
  — SQL генерируется один раз в конце, уже оптимальный.
  — Нет лишних обращений к базе.

Когда QuerySet «выполняется» (идёт запрос к БД):
  — Итерация в цикле: for obj in qs
  — Взятие среза: qs[0:5]
  — Вызов list(qs), len(qs), bool(qs)
  — Явные методы: qs.count(), qs.exists(), qs.get()

Менеджер — точка входа для работы с QuerySet.
  Model.objects — стандартный, возвращает все записи.
  Model.active  — наш кастомный, возвращает только активные.
  Менеджеров у одной модели может быть несколько.

  ВОПРОС: Регулярные выражения в URLs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/urls.py — строка 45

Два способа задать URL в Django:

path() — простой, с «конвертерами типов»:
  path('prostheses/<int:pk>/edit/', ...)
  <int:pk> — принимает только целые числа и передаёт в view как переменную pk.
  Конвертер int проверяет формат и сам преобразует строку в число.

re_path() — гибкий, с регулярными выражениями:
  re_path(r'^prostheses/(?P<pk>[0-9]+)/$', ...)
  Здесь URL описывается регулярным выражением — можно задать любой паттерн.

Разбор паттерна  ^prostheses/(?P<pk>[0-9]+)/$:
  ^             — URL начинается здесь (якорь начала)
  prostheses/   — буквальный текст
  (?P<pk>       — начало «именованной группы» с именем pk
  [0-9]+        — одна или более цифр (то же самое: \d+)
  )             — конец группы
  /$            — слеш и конец URL (якорь конца)

Захваченное значение (?P<pk>...) передаётся в view-функцию как параметр.
Пример: /prostheses/42/ → view получает pk='42' (строка, не число).

Зачем нужен re_path если есть path:
  path() покрывает 95% случаев. re_path() нужен когда:
  — URL должен соответствовать сложному паттерну
  — Нужна проверка, которую конвертеры не поддерживают
  В нашем проекте re_path используется для демонстрации — именно этого требует задание.
