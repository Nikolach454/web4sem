Смотреть: catalog/views.py — функции prosthesis_create, prosthesis_edit, prosthesis_delete

CRUD — аббревиатура: Create (создать), Read (прочитать), Update (обновить), Delete (удалить).
Это четыре базовые операции с любыми данными.

Маршруты для протезов:
  Просмотр:      /catalog/prostheses/
  Детальный:     /catalog/prostheses/1/
  Создать:       /catalog/prostheses/create/
  Редактировать: /catalog/prostheses/1/edit/
  Удалить:       /catalog/prostheses/1/delete/

Как работает форма создания/редактирования:
  При первом открытии (GET) — показывается пустая или заполненная форма.
  При отправке данных (POST) — форма проверяется, если всё верно — сохраняется,
  браузер перенаправляется на страницу объекта.
  Если есть ошибки — форма показывается снова с сообщениями об ошибках.

Как работает удаление:
  Сначала показывается страница подтверждения (чтобы не удалить случайно).
  После подтверждения (POST) объект удаляется, браузер перенаправляется в список.

Показать: создать протез через /catalog/prostheses/create/ — заполнить поля,
нажать «Сохранить» → открылась страница созданного протеза.
Показать: удалить протез — нажать «Удалить» → страница подтверждения → удалён.

  ЗАДАНИЕ: ManyToManyField с параметром through
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py — User, UserRole

Простая связь M2M (без through) — для тегов протеза:
  Prosthesis.tags = ManyToManyField('Tag')
  Здесь в промежуточной таблице хранится только пара ID: протез + тег.
  Никаких дополнительных данных не нужно.

Связь M2M с through — для ролей пользователя:
  User.roles = ManyToManyField(Role, through='UserRole')
  Промежуточная таблица UserRole содержит не только пару user+role,
  но и дополнительное поле assigned_at — дату назначения роли.

Зачем through:
  Когда нужно хранить информацию о самой СВЯЗИ, а не только о факте связи.
  Например: «пользователю назначена роль Администратора 5 января 2025».
  Без through сохранить эту дату некуда.

Показать: /admin/catalog/user/1/ — внизу inline «Роли пользователя».
Каждая строка содержит: пользователь + роль + дата назначения.
Дата назначения — это то дополнительное поле, ради которого нужен through.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция prosthesis_list()

Проблема без select_related (проблема N+1):
  Когда получаем список из 50 протезов и для каждого хотим показать его тип,
  Django делает 51 запрос к базе:
    1 запрос  — получить все протезы
    50 запросов — получить тип для каждого протеза отдельно
  При 1000 протезов — 1001 запрос. Страница работает медленно.

Решение — select_related():
  Prosthesis.active.all().select_related('prosthesis_type')
  Django делает ОДИН запрос с JOIN — получает протезы и их типы сразу.
  При любом количестве записей — всегда 1 запрос.

Когда использовать: для ForeignKey (связь «многие к одному»).
Если обращаетесь к obj.some_fk_field в цикле — нужен select_related.

Показать: /catalog/prostheses/ — в таблице отображается тип каждого протеза.
Всё это загружается единственным SQL-запросом благодаря select_related.
Можно проверить через Debug Toolbar (панель снизу): раздел SQL — будет 1 JOIN-запрос.

  ЗАДАНИЕ: prefetch_related()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция stats()

Для чего нужен:
  select_related работает для ForeignKey (один связанный объект).
  Для ManyToMany и обратных связей (один → много) JOIN создаёт дублирующиеся строки.
  prefetch_related делает отдельный запрос и объединяет данные уже в Python.

Как работает:
  User.objects.prefetch_related('roles').all()
  Шаг 1: SELECT * FROM user                              — получить всех пользователей
  Шаг 2: SELECT * FROM role WHERE id IN (1, 2, 3, ...)   — получить все роли разом
  Итого: 2 запроса при любом количестве пользователей.

Без prefetch_related:
  50 пользователей → 1 + 50 = 51 запрос (для каждого пользователя отдельно запрашиваются роли).

Когда использовать: когда в шаблоне или view обращаетесь к M2M или обратным FK
в цикле. У нас: users[i].roles.all() в цикле — нужен prefetch_related.

Показать: /catalog/stats/ — раздел «Пользователи и роли».
У каждого пользователя показаны его роли — всё через 2 SQL-запроса.

Что делает эта команда:
  pip — менеджер пакетов Python.
  install — установить пакеты.
  -r requirements.txt — читать список из файла requirements.txt.
  Команда устанавливает все пакеты с точно указанными версиями.

Зачем фиксировать версии:
  Без фиксации сегодня устанавливается Django 5.1.4, а через полгода — 5.2.0
  с изменёнными API. Код перестанет работать.
  Зафиксированные версии гарантируют одинаковое поведение везде.

Как обновить requirements.txt после установки нового пакета:
  pip install новый_пакет
  pip freeze > requirements.txt   ← перезапишет файл со всеми пакетами

Рекомендуется использовать с виртуальным окружением:
  python -m venv venv
  venv\Scripts\activate       ← Windows
  pip install -r requirements.txt
  Виртуальное окружение изолирует зависимости проекта от системных пакетов.
