  ЗАДАНИЕ: models.URLField()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/models.py — Event.website

URLField — поле для хранения веб-адреса.
Хранится в базе данных как обычный текст, но при сохранении через форму
Django проверяет что значение является корректным URL.
В HTML-форме рендерится как <input type="url"> — браузер тоже проверяет формат.

Показать:
  /admin/catalog/event/add/ — поле «Сайт мероприятия».
  Попробовать ввести «просто текст» → ошибка «Введите корректный URL».
  Ввести https://example.com → сохраняется без ошибок.

  ЗАДАНИЕ: __icontains и __contains
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция prosthesis_list()

Оба оператора ищут вхождение строки внутри поля (как SQL LIKE '%...%').
Разница — только в учёте регистра символов.

__icontains — поиск БЕЗ учёта регистра (case-insensitive):
  Ищем «протез» → найдёт «Протез», «ПРОТЕЗ», «пРоТеЗ», «протез».
  Это самый удобный вариант для пользовательского поиска.
  Применяется в строке поиска на странице каталога.

__contains — поиск С учётом регистра (case-sensitive):
  Ищем «Протез» → найдёт только «Протез», но не «протез» и не «ПРОТЕЗ».
  Полезно в ситуациях, где регистр значим (артикулы, коды, хэши).

Показать: /catalog/prostheses/
  Ввести в строку поиска «РУКА» заглавными — находит протезы типа «рука»
  (потому что используется __icontains).

  ЗАДАНИЕ: values() и values_list()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция stats()
Показать: /catalog/stats/ — раздел «Все протезы в каталоге»

Обычный QuerySet возвращает полноценные объекты Python с всеми полями.
Когда нужны только 1–2 поля из таблицы — это расточительно.
values() и values_list() позволяют получить только нужные данные.

values() — возвращает список словарей:
  Prosthesis.objects.values('name', 'price')
  → [{'name': 'Протез руки', 'price': 50000}, {'name': 'Экзоскелет', 'price': 120000}, ...]
  Удобно когда нужно передать данные в JSON или обрабатывать как словари.

values_list() — возвращает список кортежей:
  Prosthesis.objects.values_list('name', 'price')
  → [('Протез руки', 50000), ('Экзоскелет', 120000), ...]

values_list(flat=True) — плоский список одного поля:
  Prosthesis.objects.values_list('name', flat=True)
  → ['Протез руки', 'Экзоскелет', 'Бионическая нога', ...]
  Применяется когда нужен просто список значений для отображения или фильтра.
  В проекте используется для списка всех протезов на странице статистики.

Почему это эффективнее:
  Стандартный объект модели создаётся в Python со всеми методами и атрибутами.
  При values/values_list создаются простые dict/tuple — намного легче.
  На 10 000 записей разница в памяти и скорости ощутима.

  ЗАДАНИЕ: count() и exists()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — prosthesis_list() и stats()
Показать: /catalog/stats/ — раздел «Наличие данных»

count() — считает количество записей:
  Qs.count() выполняет SQL SELECT COUNT(*).
  Возвращает число — например, 42.
  Используется когда нужно знать сколько записей.

exists() — проверяет наличие хотя бы одной записи:
  Qs.exists() выполняет SQL SELECT 1 LIMIT 1.
  Возвращает True или False.
  Используется когда нужно знать «есть ли вообще что-нибудь?».

Почему exists() быстрее count() для проверки «есть или нет»:
  COUNT(*) перебирает ВСЕ строки и подсчитывает.
  EXISTS останавливается при нахождении ПЕРВОЙ строки.
  При миллионе записей разница колоссальная.

Правило выбора:
  Нужно число → count()
  Нужна проверка «есть/нет» → exists()
  Не делайте: if qs.count() > 0 → это медленно. Делайте: if qs.exists().

Показать: /catalog/prostheses/ — «Найдено: N протезов» — это count().
Показать: /catalog/stats/ — «Протезы дороже 100 000: есть/нет» — это exists().

  ЗАДАНИЕ: update() и delete()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция orm_demo()
Показать: /catalog/orm-demo/

Обе операции выполняются на уровне базы данных одним SQL-запросом,
без загрузки объектов в Python.

update() — массовое обновление:
  Находим все активные протезы без цены → деактивируем их одним запросом.
  Возвращает количество обновлённых строк.
  Намного быстрее, чем загружать каждый объект, менять поле и вызывать save().

delete() — массовое удаление:
  Находим все неактивные протезы → удаляем их одним запросом.
  Возвращает кортеж: (сколько удалено всего, словарь по моделям).
  «По моделям» — потому что могут каскадно удалиться связанные объекты.

Важное отличие от поштучных операций:
  При obj.save() и obj.delete() — Django генерирует сигналы pre_save, post_save,
  pre_delete, post_delete. Можно повесить логику (например, отправить уведомление).
  При QuerySet.update() и QuerySet.delete() — сигналы НЕ генерируются.
  Это нужно учитывать если есть привязанная к сигналам логика.

Показать:
  /catalog/orm-demo/ — кнопка «Деактивировать» (update) и «Удалить неактивные» (delete).
  Нажать «Деактивировать» → протезы без цены исчезнут из /catalog/prostheses/
  (кастомный менеджер не покажет неактивные).

  ВОПРОС: Кеш-фреймворк Django
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Зачем нужен кеш:
  Некоторые операции дорогостоящие — сложные SQL с JOIN и агрегацией,
  обращения к внешним API, тяжёлые вычисления.
  Если на странице статистики 10 таблиц с агрегациями, и её открывают 100 раз в минуту —
  это 1000 тяжёлых запросов в минуту к базе данных.
  Кеш сохраняет результат первого вычисления и отдаёт готовый при следующих запросах.

Варианты хранения кеша:
  В памяти процесса   — быстро, но теряется при перезапуске сервера, не масштабируется
  В файлах на диске   — медленнее, но не теряется
  В Redis / Memcached — быстро, масштабируется, стандарт для продакшена

Как использовать:
  data = cache.get('stats_data')      — попытка взять из кеша
  if data is None:                    — если нет в кеше
      data = дорогой_запрос()         — вычисляем
      cache.set('stats_data', data, timeout=300)  — сохраняем на 5 минут
  # теперь data использована

Инвалидация — когда данные изменились, старый кеш нужно сбросить:
  cache.delete('stats_data')

В нашем проекте кеш не используется (для простоты демонстрации ORM).
На реальном проекте страницу статистики нужно было бы кешировать.

  ВОПРОС: F expressions
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Зачем нужны F-выражения:
  Обычно чтобы изменить значение поля нужно:
    1. Загрузить объект из БД в Python
    2. Изменить значение в Python
    3. Сохранить обратно в БД
  Это три обращения к БД, плюс проблема с многопоточностью:
  два пользователя могут одновременно прочитать одно значение, оба изменят его,
  и одно изменение будет потеряно.

  F() — это ссылка на значение поля непосредственно в базе данных.
  Операция с F() выполняется в SQL одной командой, на стороне БД,
  без загрузки в Python.

Примеры применения:
  Поднять цену всех протезов на 10%:
  Без F: нужно загрузить все протезы в Python, изменить каждый, сохранить.
  С F:   один SQL UPDATE — мгновенно, безопасно, атомарно.

  Атомарный счётчик просмотров (безопасно при параллельных запросах):
  Без F: два запроса могут прочитать views=5 одновременно,
         оба запишут views=6, хотя должно быть views=7.
  С F:   SQL UPDATE SET views = views + 1 — атомарно на уровне БД.

  Фильтр, сравнивающий два поля одной записи:
  Найти мероприятия, которые начались позже их объявления:
  Event.objects.filter(event_date__gt=F('created_at'))
  Здесь F('created_at') означает «значение поля created_at этой же записи».

  ВОПРОС: Http404
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Смотреть: catalog/views.py — функция prosthesis_detail()

Что такое Http404:
  Специальное исключение Django, которое означает «запрошенная страница не найдена».
  Когда оно возникает, Django автоматически возвращает ответ с кодом 404
  и показывает страницу с сообщением об ошибке.

Два способа вызвать 404:

  Способ 1 — явный (показывает намерение разработчика):
    try:
        obj = Prosthesis.objects.get(pk=pk)
    except Prosthesis.DoesNotExist:
        raise Http404('Протез не найден')

  Способ 2 — удобный ярлык (одна строка вместо четырёх):
    obj = get_object_or_404(Prosthesis, pk=pk)
    В проекте используется именно этот способ в большинстве view.

Зачем нужен 404 а не просто показ пустой страницы:
  Корректный HTTP-статус сообщает браузеру и поисковикам что страницы нет.
  Поисковые роботы не будут индексировать несуществующие URL.
  Браузер может показать свою стилизованную страницу ошибки.

Разница DEBUG=True и DEBUG=False:
  True  → Django показывает подробную страницу с traceback — удобно при разработке.
  False → Django показывает шаблон 404.html из папки templates/ — для production.

Показать: открыть /catalog/prostheses/99999/ — страница 404.
